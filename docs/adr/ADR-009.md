# ADR-009: Lean Deterministic Evaluation Harness for Clinical RAG

**Status:** Draft  
**Date:** 2026-06-12  
**Deciders:** Ivan Beira  
**Consulted:** —  
**Informed:** Portfolio reviewers / future maintainers

## Context

ADR-007 delivered the LangGraph `StateGraph` pipeline (retrieval → grounded generation with uncertainty handling → deterministic Safety Critic → structured `ClinicalResponse`). ADR-008 subsequently strengthened the Safety Critic and related components to be fully deterministic.

We need a lightweight evaluation layer that verifies whether the user-facing clinical safety signals are reliable: confidence, citations, uncertainty notes, human-review routing, and recommended next steps. The application can already expose these fields to users, but those runtime fields are not enough by themselves; we still need an offline benchmark to check that they remain grounded, deterministic, and regression-safe after code changes.

Because this project already uses LangGraph as the orchestration layer, runtime safety and quality behavior should not be hidden in a disconnected evaluation script. Deterministic checks that affect clinical behavior must remain visible in the graph/state so future maintainers, coding agents, tests, and LangSmith traces can see what happened and why. Otherwise, important behavior can become scattered, forgotten, or accidentally bypassed during later changes.

Clinical RAG evaluation must be **deterministic by default** from the first line of code. Non-deterministic behavior would undermine reproducibility, regression detection, clinical auditability, and local/offline execution — the same problems ADR-008 was created to solve for the safety layer.

Duplicated question strings across `run.py`, tests, and ADRs have already diverged; centralizing fixtures prevents benchmark drift and false regressions.

Richer evaluation ideas were considered, including Project_3-style notebook reports, RAGAS metrics, LLM judges, content-hash judge caching, and clinical coherence rubrics. These remain interesting future options, but they are intentionally deferred for now to avoid over-engineering before the deterministic baseline is proven useful.

## Decision

Create a lean `evaluation/` package that validates the clinical RAG pipeline against the four canonical Merck questions using deterministic, metadata-aware metrics. The harness verifies that user-facing confidence, uncertainty, citations, and follow-up suggestions are consistently supported by retrieved evidence and safety-layer behavior.

The production LangGraph remains the source of truth for runtime clinical decision flow. Deterministic safety and quality gates that are relevant for every user request should be modeled as LangGraph nodes, state fields, or explicit graph transitions when that improves maintainability, testing, and LangSmith traceability. The external evaluation harness should execute the graph and inspect its final state/traces; it should not duplicate hidden clinical logic outside the graph.

In the current graph, `apply_safety_layer` runs inside the `assess_and_route` node rather than as a separate graph step; evaluation inspects the resulting `safe_response` and `assessment` fields after that node completes.

### Core Design Principles (Determinism First)

1. **Default execution is fully deterministic (Layer A)**  
   The harness and all metric functions default to deterministic mode. No randomness is allowed in metric computation. Metric functions are pure functions of final graph state and config thresholds.

2. **Deterministic metrics only in Phase 1**  
   Phase 1 measures simple, auditable signals that can be computed from the final graph state without another model call:
   - citations are present for substantive clinical answers
   - source count is available and within expected bounds
   - confidence is present and within the validated `0.0` to `1.0` range
   - uncertainty signals trigger human review when appropriate
   - recommended next steps are present for low-confidence or uncertain answers
   - warning metadata is surfaced when warning-level chunks are retrieved
   - answer/sources/metadata remain inspectable for regression review
   - latency is recorded for practical comparison

3. **LangGraph as the runtime source of truth**  
   Runtime clinical behavior belongs in LangGraph, not in hidden evaluation-only code. The evaluation harness remains external for batch execution and reporting, but it invokes the existing `run_clinical_rag_graph` (ADR-007) and inspects graph state, routing history, node logs, and future LangSmith traces.  
   The graph nodes are maintained to support deterministic operation:
   - `generate` node must accept and respect `temperature=0` (or fixed low value) during evaluation runs.  
   - `apply_safety_layer` (inside `assess_and_route`) remains purely deterministic (rule-based + Pydantic).  
   - All nodes consistently populate metadata (`section_hierarchy`, `warning_level`, page provenance) so deterministic metrics can inspect them reliably.  
   - Deterministic runtime checks such as schema validation, citation presence, uncertainty detection, confidence assessment, warning-source detection, injection safety, and human-review routing may be represented as graph nodes, state fields, or explicit graph transitions when they are part of normal user-facing behavior.
   - Phase 1 does not add benchmark/reporting nodes to the production graph.
   Lightweight deterministic instrumentation, such as timing and state-key capture, may be added when it improves traceability without changing user-facing behavior.

4. **Simple reporting first**  
   The harness produces a compact per-question table with deterministic metric values and PASS/FAIL status. It may compare hierarchical and recursive retrieval strategies, but reporting remains intentionally simple: console output plus optional `CSV`/`JSON` artifacts are enough for Phase 1.

5. **Reproducibility**  
   Identical **graph state** and `EvaluationConfig` must produce identical metric values and PASS/FAIL (Layer A). Identical **live LLM runs** are not required to reproduce identical state (Layer B); CI relies on mocked generation instead. Measured runtime latency is excluded from reproducibility guarantees.

### Determinism Scope (Two Layers)

ADR-009 uses "deterministic" at two distinct layers. Both must be explicit so CI, local runs, and portfolio demos do not contradict each other.

**Layer A — Deterministic metric computation (required, CI-gated)**  
Metric functions are pure: they take the final `ClinicalRAGState` (and optional config thresholds) and return metric values and PASS/FAIL without any additional model call, randomness, or wall-clock dependency except where latency is explicitly recorded as a non-gating metric.

Given identical graph state and identical `EvaluationConfig`, metric outputs must be identical.

**Layer B — End-to-end pipeline reproducibility (not guaranteed in Phase 1)**  
The `generate` node invokes an LLM. Even with `temperature=0`, provider APIs may return different structured answers across runs. Therefore:

- Identical questions + config + code do **not** guarantee identical `ClinicalResponse`, routing, or PASS/FAIL on live LLM runs.
- Phase 1 does **not** require LLM output caching or golden-answer regression for CI.
- Live evaluation runs are for manual regression, strategy comparison, and portfolio evidence. Live LLM variance is a Layer B concern, not controlled by the `deterministic` config flag.

**CI and unit-test default:** Mock LLM or injected `ClinicalRAGState` fixtures. CI asserts Layer A (metric logic + harness wiring), not Layer B stability.

**Evaluation run modes (Phase 1):**

| Mode | LLM | Gating | Purpose |
|------|-----|--------|---------|
| `metric_unit` | None (state fixtures) | CI | Prove each metric and threshold |
| `harness_integration` | Mock LLM (fixed JSON) | CI | Prove harness invokes graph and aggregates metrics |
| `live_eval` | Real LLM, `temperature=0` | Manual / optional | Portfolio, local regression, strategy comparison |

**Latency:** Recorded for comparison only. Latency does not affect PASS/FAIL in Phase 1 unless an explicit optional ceiling is configured later.

### Canonical Fixtures (Single Source of Truth)

The four Merck benchmark questions are defined **once** in:

`src/frontline_clinical_rag/evaluation/fixtures.py`

**Contents:**

- `CANONICAL_MERCK_QUESTIONS`: ordered list of the four clinical questions (exact strings used for all benchmark runs).
- Optional `ClinicalQuestionFixture` records: `id`, `question`, `topic` (e.g. sepsis, appendicitis), for stable CSV/JSON columns and future rubrics.

**Consumers must import fixtures; they must not redefine question strings:**

- `evaluation/harness.py`
- `run.py` (demo and eval modes)
- `tests/pipeline/test_graph.py` and evaluation tests
- README examples

**Question text policy:** Use the full, natural-language form (as in current `run.py`), not abbreviated test labels. Abbreviated variants in existing tests are replaced by fixture imports.

**Out of scope for this fixture file:** prompt-injection / guardrail cases. Those remain in `tests/` with explicit expected short-circuit behavior (`validate_input → END`, no `ClinicalResponse`).

### Phase 1 Metrics and PASS/FAIL Rules

Each metric is computed from final `ClinicalRAGState` after `run_clinical_rag_graph` completes. PASS/FAIL is deterministic (Layer A). Thresholds below are Phase 1 defaults; `EvaluationConfig` may override numeric bounds but not remove required checks without an explicit ADR change.

#### Metric definitions and default thresholds

| ID | Metric | Source fields | PASS when | FAIL when | Notes |
|----|--------|---------------|-----------|-----------|-------|
| M1 | `has_output` | `state["output"]` | `output` is a `ClinicalResponse` | missing `output`, or injection short-circuit | Benchmark fixtures use benign questions only |
| M2 | `citations_present` | `output.sources`, `output.answer` | `len(output.sources) >= 1` OR answer is non-substantive (fewer than 20 words per `ClinicalResponse` schema rule) | substantive answer (`>= 20` words) with zero sources | Aligns with `require_sources_for_substantial_answer` |
| M3 | `source_count_in_bounds` | `assessment.source_count`, config `retrieval.top_k` | `1 <= source_count <= top_k` (or `>= 1` if `top_k` unset) | `source_count == 0` on generated path | `source_count` = len(sources) on safe response |
| M4 | `confidence_valid` | `assessment.confidence` | `0.0 <= confidence <= 1.0` | outside range or missing assessment | Schema already constrains; metric catches graph bugs |
| M5 | `routing_consistent_with_assessment` | `routing_decision`, `assessment`, `safety.low_confidence_threshold` | Matches `_determine_routing_decision(assessment)` | routing disagrees with assessment policy | Pure replay of graph routing rules in eval |
| M6 | `human_review_when_required` | `assessment`, `routing_decision` | If `confidence < threshold` OR `requires_human_review` OR `has_uncertainty_signal` → `routing_decision == LOW_CONFIDENCE_ESCALATION` | safety signals present but routed `HIGH_CONFIDENCE` | Escalation path exercised |
| M7 | `uncertainty_fields_when_escalated` | `output`, `routing_decision` | On `LOW_CONFIDENCE_ESCALATION`: at least one of `uncertainty_note`, non-empty `key_findings_to_verify`, or non-empty `recommended_next_steps` | escalated but all uncertainty fields empty | **Live LLM may FAIL**; CI uses MockLLM with populated fields |
| M8 | `disclaimer_present` | `output.disclaimer` | non-empty after strip | empty disclaimer | |
| M9 | `warning_metadata_surfaced` | retrieved `documents[].metadata.warning_level`, `output.warning_level_summary` | If any retrieved chunk has `warning_level` in configured high-warning set → summary is non-empty and not only the default "no warning" string | high-warning chunks retrieved but summary ignores them | Compare against `SafetyCritic` high-warning levels |
| M10 | `safety_layer_applied` | `node_log`, `safe_response` | `"assess_and_route" in node_log` and `safe_response` is set | generated path skipped assess | |
| M11 | `full_path_executed` | `node_log` | `validate_input → retrieve → generate → assess_and_route → (format_high_confidence \| handle_low_confidence_escalation)` | missing expected nodes on generate path | |
| M12 | `latency_recorded` | harness timer | numeric ms recorded | not recorded | **Never gates PASS** in Phase 1 |

#### Aggregate PASS/FAIL

- **Per-question PASS:** all gating metrics (M1–M11) PASS for that question.
- **Run PASS:** all four canonical questions PASS for the configured retrieval strategy.
- **Strategy comparison:** same rules per strategy; harness may report pass count per strategy (e.g. hierarchical 4/4 vs recursive 3/4) without a single combined PASS.

#### Gating vs informational

- **Gating (CI):** M1–M11 except M12; M7 enforced in CI only via MockLLM/fixture states.
- **Informational:** M12 latency; optional future ceilings in Phase 2.

**LLM-dependent metrics (M7):** Phase 1 treats routing and safety signals as the primary clinical guarantees. Presence of `recommended_next_steps` on escalation is checked because it is part of the `ClinicalResponse` contract, but live LLM runs may fail M7 without indicating a graph bug. CI must not gate on M7 against a live provider; use MockLLM or state fixtures.

### Alternatives Considered and Rejected

- Putting benchmark orchestration and report generation inside the production LangGraph (rejected): Running fixtures, comparing retrieval strategies, aggregating metrics, and writing `CSV`/`JSON` reports are batch evaluation concerns, not single-request clinical inference behavior.
- Keeping all deterministic quality checks outside LangGraph (rejected): This would hide important clinical behavior from the main runtime path, make LangSmith traces less useful, and increase the risk that future maintainers or coding agents bypass or forget safety-relevant logic.
- Building a full Project_3-style reporting platform immediately (deferred): Valuable for a later portfolio/demo layer, but heavier than needed for the first useful clinical RAG benchmark.
- Making LLM judges mandatory (rejected): Would re-introduce the non-determinism problems that ADR-008 fixed for safety.
- Pure RAGAS without deterministic layer (rejected): Ignores our rich clinical metadata and cannot guarantee reproducibility without additional controls.
- Golden-file LLM output caching for CI (deferred): Layer B non-reproducibility is accepted; Layer A + MockLLM is sufficient for Phase 1.

## Non-negotiable Invariants

- Metric functions and PASS/FAIL aggregation are deterministic given identical final graph state and config (Layer A); live LLM end-to-end reproducibility is explicitly out of scope for Phase 1 CI (Layer B).
- Phase 1 does not call LLM judges or non-deterministic metric services.
- `evaluation/fixtures.py` is the only authoritative definition of benchmark question text; demos, harness, and tests import from it.
- Every benchmark evaluation run must execute the full generate path (retrieval → generation → `assess_and_route` / `apply_safety_layer` → validated `ClinicalResponse`). Benign clinical fixtures only; guardrail/injection cases are tested separately.
- The harness remains external for benchmark orchestration, strategy comparison, tabular reporting, and artifact writing.
- Runtime clinical safety and quality decisions that affect every user request must stay visible in LangGraph nodes, state fields, routing history, or explicit transitions.
- Phase 1 does not add benchmark/reporting nodes to the production graph.
- Reports and metric values must be reproducible given identical graph state and `EvaluationConfig`, excluding measured latency.
- All nodes in the LangGraph chain must support deterministic operation (`temperature=0` where applicable) and consistent metadata population so the harness can produce reliable traces.

## Consequences

**Positive:**

- Evaluation is deterministic from day one and aligned with ADR-008's safety determinism work.
- Validates whether user-facing confidence, citations, uncertainty notes, review flags, and follow-up suggestions are trustworthy across benchmark questions.
- Keeps runtime safety and quality behavior discoverable in LangGraph, improving maintainability, LangSmith traceability, and resilience against future accidental bypasses.
- Preserves clean architectural boundaries from ADR-005/007 by keeping batch benchmark/reporting logic outside the user-facing graph.
- Enables confident local/offline runs and lightweight regression tracking without turning evaluation into a separate platform too early.

**Negative / Trade-offs:**

- Phase 1 will not provide advanced clinical coherence scoring, RAGAS metrics, LLM-judge rubrics, or rich notebook-style experiment reports.
- The deterministic checks are intentionally conservative and may miss answer-quality issues that require expert or model-assisted review.
- Live eval PASS/FAIL may fluctuate with provider behavior even when the graph and safety layer are correct (mitigated by CI mode and explicit M7 policy).

## Implementation Roadmap

**Phase 1 (this ADR — deliverable):**

- `evaluation/fixtures.py` — canonical questions (single source of truth).
- `evaluation/metrics.py` — metric functions + default thresholds (table in this ADR).
- `evaluation/config.py` — `EvaluationConfig` (see fields below).
- `evaluation/harness.py` — orchestration, reporting, and run modes (`metric_unit`, `harness_integration`, `live_eval`).
- `evaluation/` package wiring with deterministic-by-default metrics that inspect final LangGraph state, routing history, node log, and trace-friendly metadata.
- Keep runtime clinical quality checks visible in LangGraph/state rather than duplicating hidden decision logic in the evaluation package.
- Update `run.py` with evaluation mode that produces simple deterministic tables for the configured strategy, with optional hierarchical vs recursive comparison.
- Unit tests that enforce Layer A deterministic behavior + harness integration test on the four questions (MockLLM).
- README updates documenting the deterministic default and run modes.
- Accept ADR-009.

**`EvaluationConfig` fields (Phase 1):**

- `deterministic: bool = True` — means Layer A metric computation only; does not imply Layer B LLM reproducibility.
- `low_confidence_threshold` — default from `AppConfig.safety.low_confidence_threshold`.
- `min_sources: int = 1`
- `run_mode: Literal["metric_unit", "harness_integration", "live_eval"]`
- `strategies: list[str] = ["hierarchical"]` — optional `["hierarchical", "recursive"]` for comparison runs.

**Phase 2 (deferred):**

- Project_3-style notebook reporting with richer per-case tables, aggregates, and versioned experiment artifacts if the evaluation output becomes important for demos or portfolio review.
- Optional RAGAS reference-free metrics if deterministic baseline results show that deeper answer-quality measurement is needed.
- Optional lightweight LLM-judge rubrics, such as uncertainty calibration or clinical utility/coherence scoring, only behind explicit feature flags, `temperature=0`, structured output, and content-hash caching.
- Additional clinical rubrics behind the same deterministic + caching guards.
- Optional non-breaking instrumentation of existing nodes for deeper per-node metrics (if needed).
- Richer experiment comparison tooling.
